02 / DESIGN FRAMEWORK

Performance-to-Puzzle Framework

Start with performance. Make the thinking playable. Expand each step for a practical example and the output to produce.

01Find the Performance GapWhat aren't people doing successfully, and why?+

In practice: For the fictional headquarters, the design need is identifying consequential emergencies amid distracting reports. In a real project, check observed work and causes first; a missing tool or unclear policy may not be a training problem.

Key moves: Spot the pattern · Gather evidence · Check the cause · Define the action

Your output: A specific practice-worthy behavior

02Make Success ObservableWhat should learners be able to do, and what counts as success?+

In practice: Given six fictional incident reports and the supplied priority criteria, players select the three consequential threats, sequence them, and explain their choices. The answer key must support a defensible result.

Key moves: GIVEN · DO · STANDARD · SCORE IT

Your output: An observable objective + success criterion

03Choose Mechanic + StoryWhat kind of puzzle will help, and how can we make it engaging?+

In practice: Sorting and sequencing make players practice prioritization. The superhero rescue gives that decision urgency; it does not replace the decision with an unrelated code puzzle.

Key moves: Select mechanic(s) · Add narrative · Sketch the flow

Your output: A matched mechanic + meaningful story

04Build the ChallengeWhat information, clues, rules, and materials will players need?+

In practice: Create six incident cards, a priority guide, a recovery board, and three correct-priority cards among plausible distractions. Verify the ordering and card-back self-check before a novice playtest.

Key moves: Required info · Create artifacts · Establish solution · Playtest everything

Your output: Playable artifacts + a verified solution

05Design Feedback + TransferHow will learners get help, know they're right, and apply the skill elsewhere?+

In practice: Matching card backs confirm the correct order. Add progressive hints, a time-up recovery route, and a brief debrief; check transfer with a new comparable set of requests.

Key moves: Debrief · Help · Update · Beyond

Your output: Hint guide + updated final materials + transfer ideas

Alignment test: Could someone win without doing the target behavior? If yes, revisit the mechanic.

Example note: the real Backup League Memory Meltdown chapter uses six incident reports, with three priority threats. The four-strip example in the Puzzle Mechanics guide is a separate construction illustration, not the live puzzle.

Match the mechanic to the learning goal

Use the decision learners need to practice as your starting point. Sorting helps people prioritize; comparing evidence helps them investigate. A physical prop or secret message can make the result satisfying, but it should not let players bypass the reasoning.

Consider Rachel Arpin's framework: Challenge → Action → Reward

Challenge: What is at stake? Action: What meaningful decision must players make? Reward: What changes when they succeed?

This is a useful lens for designing each chapter: the action should require the skill you want learners to practice, and the reward should confirm the result rather than replace the thinking. Chapter rewards can then feed into a shared finale.

04 / PRACTICAL LOGISTICS

Think about the actual people and space.

Imagine 50 attendees, 10 teams, fixed seating, and just one facilitator. The physical setup determines what will work. Prepacked, self-checking kits reduce queues; stations make more sense when movement itself is the learning goal and staffing allows it.

  • PacketsPack a labeled kit for each team with the mission, chapter pieces, criteria, hints, an answer check, and a reset guide. Avoid unnecessary trips to stations.
  • No tablesGive each team a rigid folder or lap board and large, easy-to-handle pieces so they can work together from fixed seats.
  • Self-checksInclude progressive hints, answer validation with a reason, and a time-up recovery path. One facilitator cannot check every team individually.
  • PacingTime reading and setup as well as solving. Announce clear time cues, and provide a shared ending even if some teams have not finished.
  • BackupsBring spare pieces, a printed QR/console alternative, and a simple reset diagram. Test links, connectivity, and equipment before the session.
  • AccessUse legible print, color-independent clues, flexible participant roles, and equivalent paper/digital routes. Make the decision hard, not the directions.

Rehearse the whole experience: packet distribution → team formation → access and sightlines → timer and help → shared ending → reset. In a fresh playtest, notice where players are confused by directions rather than challenged by the actual decision.
